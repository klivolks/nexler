Scaffold Go apps the Nexler way.

Nexler is Klivolks' own scaffolding CLI for the Nexler Go web framework — think django-admin startproject or rails new. It generates the handlers/services/store/models layout every app built on Nexler follows, wires new routes into an existing app, and vendors front-end static assets from npm. It's the same tool Klivolks builds its own products with, free for any developer to use.

Installation

Nexler ships as a single, self-contained binary — every scaffolding template is embedded inside it. You don't need Go or npm installed to run nexler itself; you only need Go to build the apps it generates, and npm only if you use nexler add.

Windows / macOS installer

The signed installers check for Go and npm and offer to install either if missing. If you install Nexler another way, that check simply doesn't happen — nexler keeps working regardless; you just install Go/npm yourself when a command needs them.

Build from source

git clone https://github.com/klivolks/nexler.git
# from inside the cloned repo
go build -o nexler.exe ./cmd/nexler

Place the resulting binary on your PATH. nexler version confirms it's working.

Verifying a release

Every release asset is signed with cosign using a key pair committed to the repo as cosign.pub.

cosign verify-blob --bundle checksums.txt.bundle --key cosign.pub checksums.txt
cosign verify-blob --bundle nexler-setup-1.2.3.exe.bundle --key cosign.pub nexler-setup-1.2.3.exe

Verifying checksums.txt and then matching a downloaded archive's own sha256sum against its line in that file covers the raw binaries too, without needing a separate signature per archive.

Quick start

Every flag shown below can also be left off — Nexler asks for it interactively instead, with Enter accepting the default shown. Pass every flag for scripts/CI; pass none for a guided walkthrough.

nexler create app myapp
cd myapp
go build ./...
go run main.go

Add a route to an existing app:

nexler create /purchase/verify -module purchase -submodule verify -methods GET,POST -body json

Vendor a front-end package (Bootstrap, htmx, jQuery, ...) with no CDN dependency at runtime:

nexler add bootstrap

Commands

Any flag left off a command below is asked for interactively — press Enter to accept the shown default, or pass the flag to skip the question entirely.

nexler create app

nexler create app <name> [flags…]

Scaffolds a new app with the standard handlers/services/store/models layout. Scaffolding is always fully self-contained — no network access, no git required, every template ships embedded inside the binary. The one exception: if -db selects a driver, the generated app's first go build needs one go mod tidy (network access, on your machine, not Nexler's) to fetch the driver package.

FlagDefaultDescription
-dir"."Output directory (a subfolder named after the app is created inside it).
-moduleapp nameGo module path for the generated app.
-uifalseServe the homepage from editable templates/html/home/{home,layout}.html on disk via response.HTML, instead of the built-in embedded homepage.
-authnoneWhat middleware.RequireAuth enforces: none (unverified stub), jwt (bearer token, stdlib HMAC-SHA256), session (in-memory cookie store), or both.
-remember-mefalseOnly with -auth session|both — adds a rememberMe option to auth.StartSession swapping the default 24h lifetime for 30 days.
-jwt-secret""Reuse an existing JWT signing secret instead of generating one — set when multiple apps must validate each other's tokens. Blank generates a fresh, unique secret.
-db""Comma-separated driver support to generate in db/: mongo, mysql, postgres, mssql (any subset). Only opening/closing connections — no ORM, query builder, or migrations.
-coreautoWhich -db type is the app's conventional default ("core") connection. Required only when -db selects more than one type; defaults to mongo if selected, else the first type listed.
-db-host""Core connection host. Blank leaves .env's DSN blank for you to fill in by hand; every flag below is only consulted when this is set.
-db-portconventional portDefaults to 3306/5432/1433/27017 for mysql/postgres/mssql/mongo when -db-host is set.
-db-name""Core database name.
-db-user""Core database username (blank = no auth).
-db-password""Core database password (blank = no auth). Passed/prompted in plain text — there's no masked-input prompt in this CLI.
-ui, -auth, -db, and the DB-detail flags are each independent — an app can mix any combination, e.g. a session-authenticated UI app with a Postgres core connection.
nexler create app test -ui
nexler create app test -auth jwt
nexler create app test -auth both -remember-me
nexler create app test -db postgres,mongo -core mongo
nexler create app test -db mongo -db-host localhost -db-name test

nexler create <route>

nexler create /some/path -module <name> [flags…]

Scaffolds a route inside an existing app — a leading / is what tells Nexler this is a route rather than a resource keyword like app/store/service. Generates a handler, service, store, and model file grouped under module[/submodule]. If the route already exists, this instead adds only the newly-requested methods (or missing layers) to it rather than erroring.

FlagDefaultDescription
-modulerequiredTop-level group this route belongs to, e.g. purchase.
-submodule""Nested group, e.g. verify.
-filepackage nameBase file name for the generated handler/service/store/model files. Naming a file that doesn't exist yet in an already-scaffolded package creates a genuine second handler+model file pair for this invocation's method(s), instead of appending to the original file.
-namepackage nameOverrides the identifier base for handler function names, Request/Response types, and OperationIDs (not the file/package location, which stays -module/-submodule-derived). Needed when adding a second, distinct route to an already-scaffolded package whose identifiers would otherwise collide with the first route's.
-service""Reuse an existing service package as module[/submodule]; "none" skips generating a service entirely (stop at handler + model).
-store""Reuse an existing store package the same way; "none" skips it.
-dir"."Path to the app directory (must contain go.mod).
-protectedfalseRequire auth (wraps in middleware.RequireAuth, registers in routes/protected instead of routes/public). On a later invocation, applies only to the newly-added method(s).
-methodsGETComma-separated HTTP methods: GET, POST, PUT, PATCH, DELETE. OPTIONS is automatic and always 200 OK.
-bodyjsonRequest body shape for non-GET methods: json, form, or multipart.
-responsejsonjson (response.JSON, {"data": …} envelope), html (response.HTML, renders an editable template), or raw (response.JSONRaw, no envelope).
-layoutsharedOnly for -response html: shared reuses templates/html/shared/layout.html; module gives this route its own layout copy.

A route's URL can carry named path parameters — /admin/user/{id}/profile, or a trailing {name...} catch-all (Go 1.22+ ServeMux wildcards). Every generated handler decodes them via request.DecodePath, matched to your Request struct by the same json tag convention as query/body fields, and they're documented as OpenAPI path parameters automatically. A literal ? or # in the route is rejected — use a path parameter instead.

Handler function names, Request/Response types, and OperationIDs are derived from -module/-submodule + HTTP verb, never the URL path — so adding a second, distinct route under the same -module/-submodule as an existing one (different path, overlapping verb) fails fast with an error naming the colliding identifier(s), instead of silently generating duplicate/broken code. Pass -name to disambiguate.

nexler create /purchase/verify -module purchase -submodule verify -methods GET,POST -body json -protected
nexler create /home -module home -response html
nexler create /purchase/new -module purchase -submodule verify -methods POST -name New

nexler create store / nexler create service

nexler create store|service <name> [flags…]

Scaffolds a plain, standalone service or store package — no handler, no model, no route, no aggregator wiring. <name> addresses the package as module[/submodule], e.g. purchase or purchase/verify. Nothing imports it automatically; wire it up by hand from wherever needs it.

FlagDefaultDescription
-file<pkgname>store / <pkgname>serviceBase file name for the generated file.
-dir"."Path to the app directory (must contain go.mod).
-store""Service only. Link this service's TODO comment to an already-scaffolded store, as module[/submodule] — purely informational.
 
nexler create service apps
nexler create store apps

nexler db add

nexler db add <name> -type <mongo|mysql|postgres|mssql> [flags…]

Adds a new named database connection to an existing app's .env — not to be confused with nexler init db (which provisions the core schema on an already-declared connection; this declares a new connection). If -type isn't a driver the app was originally scaffolded with, this retrofits the missing driver support first (helper package, import wiring, and — if the dialect family is new to the app — db/db.go's Connect/Close cases).

FlagDefaultDescription
-typerequiredmongo, mysql, postgres, or mssql.
-dir"."Path to the app directory.
-host""Blank leaves the DSN blank for you to fill in by hand.
-portconventional portDefaults to the type's conventional port when -host is set.
-dbname""Database name.
-user""Username (blank = no auth).
-password""Password, plain text (blank = no auth).
<name> must be a valid identifier and can't be "core" — that's reserved for the app's own default connection. The new connection is reachable as db.SQL("<name>")/db.Mongo("<name>"), but never promoted to core.
nexler db add analytics -type postgres -host localhost -dbname analytics
nexler db add reports -type mssql -dir ./myapp

nexler add — vendor a front-end package

needs network + npm
nexler add <package>[@version] [flags…]

Vendors a static asset package from npm into an existing app's templates/static/vendors/<name>/, without ever giving the app itself a package.json or node_modules. Nexler shells out to npm install <package> --prefix <scratch-tmp-dir> --no-save --no-audit --no-fund in a throwaway temp directory, then copies the package's dist/ contents (flattened) — or, if it has none, the whole package minus obvious junk (tests, docs, .git, package.json, README, etc.).

FlagDefaultDescription
-dir"."Path to the app directory.
-asderived from package nameDestination folder name under vendors/, e.g. @popperjs/core → popperjs-core.
This is one of only two Nexler operations that touch the network or shell out to another process (the other is nexler init db). It requires npm on PATH. Re-running for the same name always refreshes it — there's no -force flag. Since static assets are embedded into the app's own binary at build time, a newly vendored package isn't served until you rebuild — and Nexler never wires a <link>/<script> tag for you.
nexler add bootstrap
nexler add bootstrap@5.3.3 -as bootstrap
nexler add @popperjs/core

nexler init db

needs network
nexler init db [-dir <app-dir>]

Provisions a generated app's "core" system data on its actual core database connection (read from .env's {APPNAME}_DB_CORE_TYPE/_DSN): core_config (backing GetSetting/SetSetting), core_error_log (backing LogError, auto-called on a recovered panic or any 5xx response), core_kgate_channels (backing kgate's channel registry, if init kgate has been run), core_users, and core_services (backing API-key/service-to-service auth, if the app has -auth jwt|both) — each a table plus its own stored procedure for mysql/postgres/mssql, or a unique index for mongo. All five are provisioned unconditionally on every -db app regardless of which optional features are actually used.

This is a deliberately separate, explicit step — not run automatically by create app or by the app's own startup, since a physical database can be shared by several apps and production setups often run with a low-privilege DB user that can't run DDL at all. Every statement is idempotent — safe to run again, including against a database another app already provisioned. Requires -db to have been set at create app time.

nexler init db -dir ./myapp

nexler init kpass

local only
nexler init kpass [-dir <app-dir>]

Adds a client for KPass (Klivolks' permission-check service) to an existing app: kpass/kpass.go (Check/Allowed/Authorise, plus UserIDFromRequest when the app has -auth jwt|session|both) and KPASS_URL/KPASS_CLIENT_ID/KPASS_API_SECRET added to .env (blank, for you to fill in) if not already present.

Check(ctx, userID, resource, extra) posts to {KPASS_URL}/permission/check/ and returns KPass's full response (status, message, access, user role, user type) — kept separate from Allowed (a plain yes/no helper) so callers needing more, e.g. restricting data by role, call Check directly. Authorise(ctx, code) is a separate capability: it GETs {KPASS_URL}/api/v1/authorise?code=...&client_id=... (query params, not headers — api_secret only sent if set) to resolve a one-time login/auth code from the frontend into the user's identity, returning a flat AuthoriseResult{UserId, UserType, UserName, UserRole, OrgId}. Unlike init db, this needs no network access — pure local file scaffolding, safe to re-run.

nexler init kpass -dir ./myapp

Usage — call this from any handler you want permission-gated, typically right after (or instead of) middleware.RequireAuth:

func HandleUsersCreate(w http.ResponseWriter, r *http.Request) {
	userID, ok := kpass.UserIDFromRequest(r)  // thin wrapper over auth.Subject(r)
	if !ok {
		response.Error(w, r, http.StatusUnauthorized, "not authenticated")
		return
	}
	result, err := kpass.Check(r.Context(), userID, "myapp.users.create", nil)
	if err != nil || !kpass.Allowed(result) {
		response.Error(w, r, http.StatusForbidden, "not allowed")
		return
	}
	// result.UserRole / result.UserType are also available for finer-grained checks
	// ... proceed with the real handler logic
}

A login-style handler that trades a frontend-supplied code for the user's identity:

func HandleLoginPost(w http.ResponseWriter, r *http.Request) {
	var req loginmodels.PostLoginRequest  // req.Code from the frontend
	if err := request.DecodeJSON(r, &req); err != nil {
		response.Error(w, r, http.StatusBadRequest, err.Error())
		return
	}
	identity, err := kpass.Authorise(r.Context(), req.Code)
	if err != nil {
		response.Error(w, r, http.StatusUnauthorized, "invalid code")
		return
	}
	// identity.UserId/UserName/UserRole/UserType/OrgId — start a session or issue a JWT here
}

nexler init kgate

local only
nexler init kgate [-dir <app-dir>]

Adds a client for KGate (Klivolks' message broker): kgate/kgate.go (Subscribe/Unsubscribe/ResumeAll/Publish/HandleWebhook/Register) and five blank env vars — KGATE_CLIENT_ID, KGATE_WS_SERVER, KGATE_HTTP_SERVER, KGATE_ORIGIN, KGATE_WEBHOOK_SECRET. Also auto-wires a POST /webhooks/kgate fallback route into routes/public/public.go.

Requires the app to already have a core database connection (-db at create app time) — channel subscriptions aren't static/env-driven: Subscribe(ctx, channel) records the channel and starts a background goroutine maintaining a live WebSocket connection, durable across restarts via ResumeAll(ctx) (add this near db.Connect() in your own main.go — not wired automatically). Every event, live or via the HMAC-verified webhook fallback, dispatches to a single generated handleEvent function. Needs go mod tidy once and nexler init db before subscriptions will work.

Register also documents POST /webhooks/kgate in /openapi.json/Swagger UI (previously invisible there, unlike every route nexler create <route> generates), and subscribes to a channel literally named "test" alongside ResumeAll on startup — a built-in smoke test that the whole pipeline (core DB registry + WebSocket connectivity) works end to end. Safe to leave in (Subscribe is idempotent for an already-subscribed channel) or remove once you've confirmed kgate is wired correctly.

nexler init kgate -dir ./myapp

Usage — subscribe from anywhere (a handler, a startup routine, mid-workflow), publish from anywhere, and process every delivered event (live or via the webhook fallback) in one place:

// start listening for a channel, e.g. when an order is created
if err := kgate.Subscribe(ctx, "orders.created"); err != nil {
	log.Printf("kgate: subscribing: %v", err)
}

// publish an event to that channel from anywhere else
if err := kgate.Publish(ctx, "orders.created", map[string]any{"order_id": id}); err != nil {
	log.Printf("kgate: publishing: %v", err)
}

// kgate/kgate.go — edit handleEvent for your own processing logic
func handleEvent(ctx context.Context, channel string, payload json.RawMessage) error {
	switch channel {
	case "orders.created":
		// ... handle it
	}
	return nil
}

nexler init docker

local only
nexler init docker [-dir <app-dir>]

Adds a multi-stage Dockerfile (build + serve) and a docker-compose.yml to an existing app. The build stage's golang:<version>-alpine always matches the app's real go.mod "go X.Y" directive, and the exposed/mapped port matches the app's real {PREFIX}_PORT from .env (defaulting to 8080). .env is never baked into the image — the compose file passes it through via env_file: at container runtime instead. Refuses if either file already exists.

nexler init docker -dir ./myapp

nexler init ci

local only
nexler init ci [-dir <app-dir>] [-registry dockerhub|github]

Adds .github/workflows/release.yml: builds and pushes a Docker image whenever a GitHub Release is published. -registry picks where images go — github (GitHub Container Registry, authenticated automatically via GITHUB_TOKEN) or dockerhub (via DOCKERHUB_USERNAME/DOCKERHUB_TOKEN repo secrets you add yourself); prompted interactively if not passed. Doesn't require a Dockerfile to already exist — prints a reminder instead of refusing. Refuses if release.yml already exists.

nexler init ci -dir ./myapp -registry github

nexler init kube

local only
nexler init kube [-dir <app-dir>] [-registry dockerhub|github] [-image <ref>] [-namespace <ns>] [-replicas <n>]

Adds k8s/deployment.yaml to an existing app: a Secret (every real value from .env), a Deployment (references the Secret via envFrom, TCP readiness/liveness probes on the app's port, conservative default resource requests/limits), and a ClusterIP Service — three ----separated documents in one file. Unlike init ci's workflows (which resolve an image reference at workflow-run time via GitHub's own context variables), this file is applied directly by kubectl, so it needs a concrete image reference baked in at scaffold time: -image sets it directly, or -registry github derives ghcr.io/<owner>/<repo>:latest straight from go.mod's module path (erroring if it isn't github.com/<owner>/<repo>-shaped — nexler never shells out to git to guess an owner), or -registry dockerhub prompts for your Docker Hub username and derives <user>/<repo>:latest.

-namespace is left out of every resource by default (kubectl's -n/current context decides) unless set explicitly; -replicas defaults to 1. k8s/deployment.yaml is added to .gitignore — unlike docker-compose.yml (which only references .env by path at container runtime), the Secret document here embeds .env's actual values, since Kubernetes has no equivalent way to read a local file at deploy time. Refuses if k8s/deployment.yaml already exists.

nexler init kube -dir ./myapp -registry github
nexler init kube -dir ./myapp -image ghcr.io/me/myapp:latest -replicas 3

nexler update

local only
nexler update [-dir <app-dir>]

Brings an existing app's Nexler-owned files — ones you generally don't hand-edit — up to date with whatever the current nexler binary knows how to generate, without needing to trigger it as a side effect of create <route>. Covers things like openapi/openapi.go (regenerated when it predates a field Nexler now sets) and response/response.go (missing helpers appended, never rewritten). Generated app architecture

Every app produced by nexler create app follows a fixed, layered structure. main.go calls routes.Register(mux) once and is never edited again after the initial scaffold — new routes are added purely by running nexler create <route>, which wires itself into routes/public/public.go or routes/protected/protected.go automatically.

handlers/    HTTP handlers — decode request, call service, write response
services/    business logic, orchestration
store/       persistence via the Store interface
models/      request/response and domain structs
middleware/  auth, logging, recovery, etc.
routes/      routes.go + public/protected aggregators
openapi/     in-process OpenAPI registry → /openapi.json
request/     decode helpers a handler calls into its Request struct
response/    JSON envelope helpers a handler calls to write its result
apiclient/   fetch/axios-style helpers for calling other HTTP APIs
config/      loads {APPNAME}_-prefixed env vars once, at startup
.env         editable starting point for the app's env vars
auth/        only with -auth jwt|session|both
db/          only with -db mongo|mysql|postgres|mssql
core/        only when -db is set — app-wide system data
kpass/       only after `nexler init kpass`
kgate/       only after `nexler init kgate` (needs -db)

Request decoding & response envelope

Every generated handler method decodes into its Request struct via one request package call, and writes its result via the response package — kept consistent by construction, not convention.

DECODE

request package

DecodeQuery for GET (always query-params-only). Otherwise whichever of DecodeJSON/DecodeForm/DecodeMultipart matches -body. A route with {name} path segments also gets a DecodePath call, matched by the same json tag as every other source.

RESPOND

response package

response.JSON(w, status, v) → {"data": v}. response.Error(w, r, status, msg) → {"error": msg}, and on a -db app auto-logs every 5xx to the core database, best-effort. response.JSONRaw skips the envelope; response.HTML renders an editable template.

Handlers only decode-then-respond; the actual service call is left as a // TODO: call <pkg>'s service with req comment — wiring it in is a deliberate, separate step you do by hand.

Idempotent route wiring

Generated files carry fixed marker comments that later CLI invocations anchor on to insert new code without reparsing Go — so re-running nexler create <route> against an already-scaffolded route only ever adds what's missing.

MarkerWhereWhat gets inserted there
// nexler:routesroutes/public(or protected)/*.goNew route imports and Register(mux) calls.
// nexler:handlershandlers/.../<file>.go (one or more per package)New per-method handler functions when adding -methods to an already-scaffolded -file.
// nexler:registerhandlers/.../<file>.go (exactly one per package — the package's primary file)New mux.HandleFunc/openapi.Register calls, for every method regardless of which file its handler is defined in.
// nexler:modelsmodels/.../<file>.go (one or more per package)New Request/Response struct pairs.
If a marker is missing (e.g. a route scaffolded before this feature existed, or a hand-edited file), the insert fails with an error naming the exact marker text to add back by hand — it never silently guesses a location.
A package's handler/model code can span more than one file. -file names the specific handler/model file this invocation targets: if it already exists, new methods are appended to it; if it doesn't, a genuine new file pair is created for them (with no Register func of its own, since Go permits only one per package). Either way, registration wiring always lands in the package's one primary file.
Adding a second, distinct route to an already-scaffolded package (same -module/-submodule, different path, overlapping verb) is checked for handler/type/OperationID collisions across every file in the package before anything is written — since identifiers are derived from -module/-submodule + verb, not the URL path, two different routes sharing those would otherwise generate duplicate/colliding code. Pass -name to give the new route distinct identifiers (this also disambiguates its HTML content file, for -response html routes).

Key concepts

Authentication (-auth)

none jwt session both

middleware.RequireAuth — what every -protected route wraps its handlers in — is generated differently per -auth choice. jwt generates auth/jwt.go (stdlib-only HS256, IssueJWT/VerifyJWT). session generates auth/session.go — an in-memory map behind a mutex plus an HttpOnly/SameSite=Lax cookie (StartSession/SessionFromRequest/EndSession); lost on restart, not shared across instances by design. both generates both, and RequireAuth tries the bearer token first, falling back to the session cookie — one protected route serves API and browser clients at once.

Whichever mechanism verifies the caller, the resulting subject (userID) is attached to the request's context via auth.ContextWithSubject; any protected handler reads it back with auth.Subject(r) (subject string, ok bool). No /login//logout route is ever generated — call auth.IssueJWT/auth.StartSession from your own login handler once credentials are verified.

Usage — a login handler you write yourself (scaffolded separately, e.g. nexler create /login -module auth), calling the generated primitives once credentials check out:

// -auth jwt or both
token, err := auth.IssueJWT(userID, name, org, userType, userRole, 24*time.Hour)
response.JSON(w, http.StatusOK, LoginResponse{Token: token})

// -auth session or both
auth.StartSession(w, userID, false)  // rememberMe if -remember-me was set
response.JSON(w, http.StatusOK, LoginResponse{})

// any protected handler downstream
userID, ok := auth.Subject(r)

API-key (service-to-service) auth

Apps with -auth jwt|both and -db set also get middleware.RequireServiceAuth — a second, wholly separate auth wrapper for app-to-app calls, checking the X-Api-Key header against a new core_services table. It never falls back to/from RequireAuth: a route is either user-facing (RequireAuth) or service-only (RequireServiceAuth), so a service-only route can never accidentally accept an end-user JWT. The API key must never be embedded in any UI-facing code — treat it like a database credential.

core.CreateService(ctx, name) generates a random key, stores only its SHA-256 hash, and returns the plaintext key exactly once — it's never retrievable again. VerifyServiceKey/RevokeService/ListServices/GetService round out the set; on success, the calling service's name is attached via a new auth.ContextWithService/auth.Service(r) pair, kept as a distinct context key from the user Subject. A generated Swagger-documented admin API (/admin/services//admin/users) wraps these functions for you — see below.

Usage — a route meant to be called only by another backend service, never a browser:

mux.HandleFunc("POST /internal/sync", middleware.RequireServiceAuth(func(w http.ResponseWriter, r *http.Request) {
	name, _ := auth.Service(r)  // the calling service's core_services Name
	// ...
}))

A companion core_users table (core.GetUser/CreateUser/SetUserStatus/ListUsers) is a minimal local record, not a profile store: UserId is the same value as the JWT sub claim, plus Username/UserRole/UserType and a Status kill-switch. Real profile data (name, email, etc.) stays wherever it already lives.

Admin API: /admin/users & /admin/services

Every -auth jwt|both + -db app also gets a Swagger-documented admin API wrapping the core functions above — hand-authored, not routed through nexler create <route>'s generic machinery, since these are infrastructure endpoints with real field definitions from day one. Wired into routes/protected/protected.go automatically, same as kgate's webhook route.

Method & pathCalls
GET /admin/userscore.ListUsers — no pagination
POST /admin/userscore.CreateUser — create/upsert
GET /admin/users/{id}core.GetUser
PATCH /admin/users/{id}/statuscore.SetUserStatus
GET /admin/servicescore.ListServices — metadata only, never keys
POST /admin/servicescore.CreateService — key in the response exactly once
GET /admin/services/{name}core.GetService — metadata only
POST /admin/services/{name}/revokecore.RevokeService
Every route wraps only in middleware.RequireAuth — that confirms the caller is authenticated, not that they're allowed to manage other users/services. Add your own authorization check (e.g. kpass.Check, once nexler init kpass has been run) before relying on this in production — deliberately left as a TODO in the generated code rather than assumed by nexler.
curl -X POST /admin/services -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"billing-svc"}'
// {"name":"billing-svc","key":"a1b2c3..."}  -- key shown exactly once

Database connections (-db) & the "core" connection

-db is deliberately scoped to connection lifecycle only — opening at startup, closing at shutdown. No query builder, ORM, or migrations. Which drivers are compiled in is a scaffold-time decision (-db's value); which named connections exist and where they point is pure .env/runtime config — {APPNAME}_DB_CONNECTIONS lists comma-separated connection names, each with its own _TYPE/_DSN. Adding or removing a connection later is just an .env edit, never a re-scaffold — use nexler db add for that.

Every -db-enabled app gets one connection pre-populated under the conventional name "core". db.Connect() (called from main() at startup) opens every declared connection up front, failing fast if one can't be reached; db.Close() is wired into a graceful shutdown on SIGINT/SIGTERM.

HTML responses (-response html)

A route scaffolded with -response html gets response.HTML(w, r, module, name, title, data) instead of response.JSON. Unlike everything else in the framework, this reads its content file and layout.html straight off disk on every request — not from the embedded binary — so you can edit the page without rebuilding. Content is rendered first (auto-escaped via html/template), then embedded as {{.Content}} inside the layout.

Query helper packages: mongo / mysql / postgres / mssql

Generated whenever the matching -db type is selected — simplified, struct-based CRUD helpers on top of the raw driver, so store/ code isn't hand-rolling query strings for common cases.

t := mysql.Conn("core").Table("users")
users, err := mysql.Get[User](ctx, t, User{Active: true})
one, err  := mysql.GetOne[User](ctx, t, User{ID: id})
err = mysql.Insert(ctx, t, User{ID: id, Name: "x"})
err = mysql.Update(ctx, t, User{ID: id}, User{Name: "y"})  // filter, then patch
err = mysql.Delete(ctx, t, User{ID: id})
rows, err := mysql.Query[Report](ctx, mysql.Conn("core"), "select * from tbl_y")

Field matching uses a struct's non-zero fields (AND'd together; a slice ORs each element), mapped via the db tag (or bson for Mongo). Insert writes every field, zeros included; Update patches only non-zero fields — worth remembering, since the two are intentionally asymmetric. Query/Call (or Aggregate for Mongo) are the raw escape hatches for anything the struct-filter model can't express.

apiclient — calling other HTTP APIs

Always generated (pure stdlib, no dependency). Fetch/axios-style helpers for the outbound direction — calling other services, as opposed to request/response which handle this app's own inbound traffic.

resp, err := apiclient.Get(ctx, url, headers)
resp, err  = apiclient.Post(ctx, url, headers, body)
var out MyType
err = resp.JSON(&out)

Every call is synchronous — the body is fully drained and the connection released back to the pool before the call returns, so you always get a plain *Response{StatusCode, Header, Body}, never a raw *http.Response you could forget to close.

Runtime configuration — config & .env

config.C is ready before main() runs, reading env vars namespaced per app as {APPNAME}_HOST/{APPNAME}_PORT/{APPNAME}_SWAGGER_ENABLED (default true)/{APPNAME}_API_BASE_PATH (no default). .env, scaffolded at the app root, is read by a hand-rolled parser — no third-party dependency, consistent with the generated go.mod having none. A key already present in the real environment always wins over .env — it's a committed-or-not local default, never an override mechanism.

{APPNAME}_SWAGGER_ENABLED gates GET /swagger and GET /openapi.json — set it to false in production to 404 both. The check happens inside each handler, not by leaving the routes unregistered: Go's net/http.ServeMux treats GET / (every app's homepage route) as a subtree pattern that would otherwise silently catch an unregistered /swagger//openapi.json and serve the homepage instead of a 404. Every other route is unaffected.

{APPNAME}_API_BASE_PATH documents the path prefix an external gateway mounts this service under (e.g. /api/my-service), left unset by default for direct/local access. When set, openapi.Spec adds a relative servers[0].url entry to /openapi.json, so Swagger UI's "Try it out" requests resolve correctly whether the app is hit directly or through the gateway — it's purely documentational and never affects actual route registration or matching.
